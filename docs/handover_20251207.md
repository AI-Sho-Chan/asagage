# ASAGAKE V2 引継ぎメモ (2025-12-07)

## 1. 週末 VM バッチの軽量化（minute_cache / opt30 キャッシュ）

- 対象環境: `asagake-weekend-vm` 上の `~/asagage` リポジトリ。
- 目的: 週末バッチの**ロジックは変えずに**、I/O 負荷とディスク使用量を下げる。

### 1-1. opt30 キャッシュの定期クリア

- 変更ファイル: `vm_run_weekend_only.sh`
- 追加処理（週末バッチの最初に実行）:

  ```bash
  # Non-essential opt30 cache can grow very large; clear it once per weekend run
  if [ -d "cache/opt30" ]; then
    rm -rf cache/opt30/*
  fi
  ```

- 意味:
  - `cache/opt30/...` は `bt_opt30_forward.py` が使う**一時キャッシュ**で、
    なくてもバックテスト結果の再現性には影響しない前提。
  - ここが肥大化して `/dev/root` が枯渇し、`OSError: [Errno 28] No space left on device` で
    週末バッチが落ちていたため、**週末バッチ開始ごとに全削除**するようにした。

### 1-2. minute_cache 更新の一元化

- これまで:
  - `vm_run_weekend_only.sh` が

    ```bash
    python tools/update_minute_cache.py \
      --codes-file "$UNIVERSE_FILE" \
      --universe-glob "data/universe/topvol_*.csv" \
      --universe-limit 800 \
      --history-days 60 \
      --backfill-days 120 \
      ...
    ```

    で Top300 向けの深掘り minute_cache を 1 回実行。
  - その後 `scripts/nightly_build_candidates.py` が `--cache-refresh-weekend` を付けて呼ばれており、
    各 `bt_opt30_forward` の coarse/refine 実行ごとに `--cache-refresh` が走っていた。

- 変更内容:
  - `vm_run_weekend_only.sh` の weekend 本番 run を以下のように変更。

    ```bash
    python scripts/nightly_build_candidates.py \
      --universe-mode yahoo-top --universe-size 300 \
      --universe-source "$UNIVERSE_FILE" \
      --lookback 60 --chunk-days 5 --train-days 12 --forward-days 4 \
      --min-train-trades 10 --min-forward-trades 2 --forward-pf-min 1.3 \
      --disable-minute-cache \
      --min-forward-winrate 0.60 --gap-guard-abs-bp 80 --gap-guard-dir-bp 40 \
      --slipbp 4 --feebp 4 --liquidity-quantile 0.3 --jobs 16 \
      --run-type weekend --plan-profile weekend \
      --enable-asha --enable-bayes --bayes-trials 60 --bayes-timeout 600 \
      --mask-ineffective --mask-window 20 --mask-threshold 1.05 \
      --enable-rd-windows \
      --enable-market-features --headless --coeff-history-days 5 \
      --target-date "$TARGET_DATE"
    ```

    - 以前付けていた `--cache-refresh-weekend` は削除。
    - `--disable-minute-cache` を追加し、`nightly_build_candidates.py` 内部からの
      `tools/update_minute_cache.py` 呼び出しを止めている。

  - 同じファイル内の weekday-style sanity run についても、

    ```bash
    python scripts/nightly_build_candidates.py \
      ... \
      --run-type weekday --plan-profile weekday \
      --enable-asha --enable-bayes --bayes-trials 32 --bayes-timeout 300 \
      --mask-ineffective --enable-market-features \
      --disable-minute-cache \
      --min-forward-winrate 0.60 --headless --coeff-history-days 5 \
      --target-date "$TARGET_DATE"
    ```

    のように `--disable-minute-cache` を付与。

- 効果:
  - minute_cache の更新は `vm_run_weekend_only.sh` 冒頭の
    `tools/update_minute_cache.py --history-days 60 --backfill-days 120` **1回に集約**される。
  - `nightly_build_candidates.py`・`bt_opt30_forward.py` 経由の冗長な minute_cache 更新が消えるため、
    Yahoo API へのリクエストとディスク I/O が減り、週末バッチ全体の実行時間・安定性が向上する。
  - WF ロジック自体（60営業日ぶんの 1分足を使う）は**全く変えていない**。

- VM への反映手順:
  - Windows 側で `git push` 済みなので、VM では

    ```bash
    cd ~/asagage
    git fetch origin
    git pull --ff-only
    ```

    を実行しておけば OK。
  - 週末バッチは `~/run_weekend_only.sh` から起動しているので、
    必要に応じて

    ```bash
    cp ~/asagage/vm_run_weekend_only.sh ~/run_weekend_only.sh
    chmod +x ~/run_weekend_only.sh
    ```

    で最新スクリプトを反映させる。

## 2. NIGHTLY 候補の Live/Demo クラス & 予算倍率（BudgetFactor）

- 目的:
  - `output/excel/NIGHTLY_YYYYMMDD/*/candidates_YYYYMMDD.csv` に対して、
    「どのコンボを Live 側の有力候補にするか」「どの程度の予算を載せるか」を
    機械的に提案できるようにする。
  - 実際の発注は引き続き `ASAGAKE.xlsm` + VBA が行うが、
    Python 側で `Live/Demo クラス` と `BudgetFactor` を出しておくことで、
    将来 Excel 側の数量計算に組み込みやすくする。

### 2-1. `analysis/summarize_nightly_candidates.py` に Live/Demo 提案を追加

- 変更ファイル: `analysis/summarize_nightly_candidates.py`
- strong コンボ抽出関数 `summarize_strong_combos` を拡張。
- 抽出条件（従来どおり）:
  - `forward_pf_eff >= 1.3`
  - `forward_winrate >= 0.6`
  - `forward_trades >= 10`
- これらを満たす行に対して、以下の2列を追加して出力:
  - `live_demo_class`: `LIVE_STRONG` / `LIVE_BASE` / `DEMO_ONLY`
  - `budget_factor`: `2.0` / `1.0` / `0.5`

#### 判定ロジック（1コンボ単位）

- まず、`forward_pf_eff`・`forward_winrate`・`forward_trades` に加えて、
  期待bp 列 `forward_exp_bp` があれば数値化して使用。
  - PF の極端な値（999 など）は、判定時は `1.0〜5.0` の範囲にクリップして扱う。

- 判定条件:

  - **LIVE_STRONG / budget_factor = 2.0**
    - `forward_trades >= 30`
    - `forward_winrate >= 0.70`
    - クリップ後 PF `>= 1.8`
    - `forward_exp_bp >= 10` （平均 +10bp 以上）

  - **LIVE_BASE / budget_factor = 1.0**
    - `forward_trades >= 15`
    - `forward_winrate >= 0.60`
    - クリップ後 PF `>= 1.3`
    - `forward_exp_bp >= 5`

  - **DEMO_ONLY / budget_factor = 0.5**
    - 上記 strong 抽出条件は満たすが、
      取引数・PF・期待bp が上2段階に届かないもの。
    - DEMO では回す価値はあるが、Live ではロットを落として慎重に見る想定。

- 出力:
  - `analysis/nightly_strong_candidates.csv` に、
    既存列 `date_tag, plan_tag, Ticker, SignalMode, session, forward_pf_eff, forward_winrate, forward_trades` に加え、
    `live_demo_class, budget_factor` を追加して書き出す。
  - コマンド例（12/4・12/5 分の集計）:

    ```bash
    cd C:/AI/asagake
    python analysis/summarize_nightly_candidates.py --date-tags 20251204 20251205
    ```

- 想定される活用方法:
  - `LIVE_STRONG`（factor=2.0）: AM0930〜AM1030 j-only の中でも特に安定している銘柄・プラン。
    - 将来的に **Live モード + 大きめ予算** の候補。
  - `LIVE_BASE`（factor=1.0）: Live 側に置いてよい標準ロット候補。
  - `DEMO_ONLY`（factor=0.5）: DEMO モード中心で回しつつ、実績が溜まれば昇格を検討。

### 2-2. 今後の拡張アイデア（まだ未実装）

- `BudgetPerTicker` と `LotSize` を使った Excel 側との連携:
  - `ASAGAKE.xlsm` の NewDashboard では、
    - `BudgetPerTicker`: 銘柄ごとの最大投下資金（円）
    - `LotSize`: 1 取引あたりの株数
    が既にパラメータとして存在し、
    VBA で

    ```vb
    qty = Int(budgetPerTicker / priceForQty / lotSize) * lotSize
    ```

    という形で数量を決めている。
  - 将来的には、夜間集計で出した `budget_factor` を候補CSV側に埋め込み、
    VBA 側で

    ```vb
    effBudget = BudgetPerTicker * BudgetFactor
    qty = Int(effBudget / priceForQty / lotSize) * lotSize
    ```

    のように読み込むことで、
    「基準予算はダッシュボードで指定しつつ、期待値に応じて 0.5× / 1× / 2× の配分を自動化」
    する設計が可能。

- Live/Demo の自動切り分け:
  - `live_demo_class` に応じて、
    - `LIVE_STRONG / LIVE_BASE` のみ実発注対象
    - `DEMO_ONLY` は DEMO モードだけ動かす or Live 時は qty=0 にする
    といった制御を `state/strategy_rules.ini` か新しい設定ファイルで持たせる案も検討中。
  - 現時点では **レポートレベルの提案のみ** で、実際の Live/Demo スイッチは
    これまで通り NewDashboard 上の「Live Start / Demo Start」ボタンで切り替える。

### 2-3. 2025-12-04 / 2025-12-05 の分布（実績）

- 2025-12-04, 2025-12-05 の weekend NIGHTLY を対象に

  ```bash
  python analysis/summarize_nightly_candidates.py --date-tags 20251204 20251205

  python - << 'PY'
  import pandas as pd
  df = pd.read_csv("analysis/nightly_strong_candidates.csv")
  print("total strong combos:", len(df))
  print(df["live_demo_class"].value_counts())
  PY
  ```

  を実行した結果:

  - `total strong combos`: 65
  - `live_demo_class` 内訳:
    - `LIVE_STRONG`: 10
    - `LIVE_BASE`: 24
    - `DEMO_ONLY`: 31

- 意味:
  - strong 抽出条件を満たす 65 コンボのうち、
    約 15% が「かなり強くてサンプルも豊富」（LIVE_STRONG）、
    約 35% が「十分 Live 候補」（LIVE_BASE）、
    残り約 50% が「まず DEMO 中心で検証する」（DEMO_ONLY）という分布になっている。
  - この比率は「全部 Live ではなく、上位 1/2〜2/3 を Live 側に寄せる」方針と整合的であり、
    今後の Live/Demo 線引き・BudgetFactor 連携のベースラインとして扱う。
