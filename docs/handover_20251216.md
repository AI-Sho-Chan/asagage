## 1) 12/12（金）16:30 に週末バッチが走らなかった原因と対策
### 何が起きた？（結論）
- VM は **12/12（金）16:15（日本時間）に起動**していました（Cloud Scheduler）。
- その後 **12/12（金）16:30（日本時間）に自動実行（cron）は起動**しました。
- しかし、実行された `~/run_weekend_only.sh` が **Windows 由来の改行（CRLF）や BOM（先頭の見えない文字）**を含んでおり、Linux が正しく読めずに **即終了**しました。
  - 証拠: `~/cloud_logs/cron_stdout.log`（12/12 16:30 更新）に次のエラーが残っていました。
    - `...: not found`
    - `set: Illegal option -o pipefail`

### どう直した？（再発防止）
- VM 側の `crontab` は **Git 管理下の** `~/asagage/vm_run_weekend_only.sh` を直接実行する構成に統一しました。
  - これで、Windows から `scp` して `~/run_weekend_only.sh` を置き換える運用を避けられます。
- cron は `CRON_TZ=Asia/Tokyo` を使い、**毎週金曜 16:30（日本時間）**で固定です。
- 週末バッチの最後に VM を自動停止してコストを抑えるようにしています（`vm_run_weekend_only.sh` 内の `shutdown`）。

### 次の金曜は走る？（チェック結果）
- 走る見込みです（設定確認済み）。
  - Cloud Scheduler: `start-weekend-vm` が **ENABLED**（金曜 16:15 JST）
  - Cloud Scheduler: `stop-weekend-vm` が **ENABLED**（土曜 23:00 JST）

## 4) Top200「常連」銘柄の 1分足データ保存（永久保存）
目的:
- 週末バッチのネット取得を減らして高速化する（次回以降が速くなる）。
- Yahoo 側で古い 1分足が消えても、こちらで保存しておけば 90日・120日と伸ばせる。

方針（合意済み）:
- 「Top200 常連」を週次 TopVol から作り、**一度 Top200 に入った銘柄は、その後外れても永久に保存対象**にする。

実装:
- 常連リスト更新: `tools/build_top_regulars_universe.py --update-ever`
  - 保存先: `data/universe/top_regulars_ever.csv`
- 1分足を毎日更新: `scripts/run_update_regulars_1m.ps1`（Windows のタスクで動かす）

注意:
- Yahoo の都合で「昔の日付を後から取り直す」のは成功しない日があります。
- ただし、**一度保存できた日付を再取得し直すことは基本的にありません**（既存ファイルがあればスキップします）。
