## 2025-12-02 VWAP 回帰フィルタ導入と 60日WF 安定仕様

- 本ログは 2025-12-01 の Top300 ユニバース拡張に続く変更点をまとめたもの。  
  入口 (coarse 前) のユニバース選定に「VWAP 回帰のしやすさ」を反映しつつ、WF 窓を一旦安定仕様 (lookback=60, train=12, forward=4) に戻している。

### 1. 週末 Yahoo-universe への VWAP 回帰フィルタ

- 対象コード: `scripts/nightly_build_candidates.py`
- 適用条件:
  - `--universe-mode yahoo-top`
  - `run_type=weekend` (明示 or `--run-type auto` で土日が解決されたケース)

- ロジック概要:
  1. `build_yahoo_universe` の出力 (`NIGHTLY_<date>/universe_*.csv`) から `code` 列を読み、週末 coarse 対象の Yahoo-universe を構成。
  2. `compute_vwap_revert_stats` を用いて、各コードについて VWAP 回帰統計を計算:
     - `VWAP_revert_prob` (乖離>=J_th のイベントが max_bars 本以内に VWAP±ε*ATR に戻る確率)
     - `avg_bars` (戻るまでにかかる平均本数)
     - パラメータは現状:
       - `lookback_days=60`
       - `j_threshold=1.0`
       - `max_bars=30`
  3. universe 内での順位 (0〜N-1) から簡易的な「流動性 quantile」を算出:
     - 最上位コードの quantile が 1.0、最下位が 0.0 となる線形マッピング。
  4. `VWAP_revert_prob` と quantile に応じて採用ルールを適用:
     - `prob >= 0.70` (強い VWAP 回帰銘柄):
       - `quantile >= 0.20` なら採用 (流動性閾値を少し緩める)。
     - `0.50 <= prob < 0.70` または prob が計算できなかった銘柄:
       - 従来どおり `quantile >= 0.30` で採用。
     - `prob < 0.50` (VWAP 回帰しにくい銘柄):
       - 原則除外だが、`quantile >= 0.50` の「超高流動銘柄」のみ採用。
  5. 生き残り銘柄数が極端に少ない場合は安全側にフォールバック:
     - しきい値: `min_keep = max(10, len(codes_u) // 10)`  
       → 生き残りが 10 銘柄未満、または元の 1/10 未満のときは、フィルタ前の Yahoo-universe をそのまま使用。
  6. フィルタ後のユニバースは `NIGHTLY_<date>/universe_vwap_filtered.csv` として保存され、
     以後の coarse/refine 呼び出しはこのファイルを `--codes-file` として使用。

- ステータス出力 (`logs/nightly_status.txt`):
  - `step=universe` で以下のようなメッセージを出力:
    - `Yahoo universe ready (VWAP filter applied)`
    - `Yahoo universe ready (VWAP filter skipped: too few survivors)`
    - `Yahoo universe ready (VWAP filter error: ...)`
  - これにより、「VWAP フィルタが実際に効いたか／フォールバックしたか」を後から確認可能。

### 2. WF 窓の安定仕様 (60日 / 12+4) へのロールバック

- 対象ファイル: `vm_run_weekend_only.sh` (ローカル側 canonical)
- 週末 coarse/refine の WF 窓を一旦次の設定に戻した:
  - `--lookback 60`
  - `--chunk-days 5`
  - `--train-days 12`
  - `--forward-days 4`
- ねらい:
  - 新しい VM 環境で minute_cache が十分溜まるまでは、  
    「train+forward が必要とする営業日数 > 実際の 1分足日数」という崩壊パターンを避ける。
  - まずは「Top300 + 60日WF + minute_cache 深掘り + VWAP フィルタ」という組み合わせで安定運用し、  
    データが十分に溜まってから `train_days` / `forward_days` を段階的に伸ばす。

### 3. Top300 常連銘柄と minute_cache の関係

- Top300 マスターユニバース:
  - `tools/build_master_topvol_universe.py` が
    - `data/universe/dekidaka*.csv`, `neagari.csv`, `nesagari.csv`, `yori_neagari*.csv`, `tick.csv` など  
      日々のスクリーニング CSV を union して master 集合を作成。
    - その master をもとに `build_weekly_topvol_universe.py` を呼び出し、
      直近 5 営業日の「終値×出来高」合計で Top300 を `data/universe/topvol_<date>.csv` に出力。
  - この Top300 は「週間売買代金上位 300 (≒Top200 常連＋その周辺)」として扱う。

- minute_cache との連携:
  - Windows 側の日次タスク (`scripts/run_update_today_1m.cmd` 等):
    - `tools/update_minute_cache.py --universe-glob data/universe/topvol_*.csv --universe-limit 1000 --codes-file output/excel/candidates_nextday.csv --history-days 1 --backfill-days 0`
    - → 過去に生成された `topvol_*.csv` 群と、直近候補銘柄を対象に 1日ずつ minute_cache を更新。
  - 週末 VM 側 (`vm_run_weekend_only.sh`):
    - `tools/update_minute_cache.py --codes-file topvol_<TARGET_DATE>.csv --universe-glob data/universe/topvol_*.csv --universe-limit 800 --history-days 60 --backfill-days 120 ...`
    - → 週次 Top300 について、1分足を 60〜120 営業日分まで一気に深掘り。
  - 結果として、「週間売買代金 Top200〜300 の常連銘柄」は、
    - 平日の日次更新＋週末の深掘りの両方から 1分足が蓄積され、
    - `bt_opt30_forward.py --use-local-raw` のローカルソースとして利用される。
