## 2) 原因：VMが起動できなかった（Google側の一時的な不足）
- Cloud Scheduler の start ジョブは 16:20（JST）に VM 起動を試みています。
- ただし Compute の start 操作が 503 で失敗していました。
  - エラー：`ZONE_RESOURCE_POOL_EXHAUSTED`
  - 内容：`n2-highcpu-16` が `asia-northeast1-a` で一時的に確保できず
- その結果：
  - VMが起動しない
  - VM上の `cron(16:30)` が動かない
  - 週末バッチも動かない

## 3) 再発防止（方針）
「バッチが動かない原因は “バッチ” ではなく “VM起動失敗”」なので、起動面に対策を入れる。

- 起動再試行を増やす：同じ start を 17:00 / 18:00 / 19:00 でも実行（起動できるタイミングを拾う）
- 自動停止：週末バッチ終了後に VM を自動停止（`vm_run_weekend_only.sh` の `AUTO_SHUTDOWN=1`）
- （必要なら）VMのマシンタイプ変更：起動しやすいタイプへ変更（最後の手段）

## 4) 「Import すると1銘柄しか出ない」現象の整理
実際には、原因が1つではなく「複数パターンが混ざっている」可能性が高いです。

- `logs/vba_events.log` に `ImportCandidatesV2 done imported=1` と `imported=27` の両方が記録されています。
- つまり「いつもCSVが1行」というより、
  - CSVが小さい / 途中までしか書けていない
  - Import処理が途中で止まる（無言で抜けている）
  - 安全装置（小さすぎるCSVを読んだ時にダッシュボードを消さない保護）で実質スキップ
  などの可能性があります。

切り分けの最短手順：
- Import直後の `logs/vba_events.log` の `ImportCandidatesV2 done ...` 行を見て、
  - `approxRecords` / `parsedRecords` / `nonEmptyLines` がいくつか
  を確認します（ここに原因がほぼ出ます）。

## 5) 次にやること（運用）
- 週末VM：起動のリトライを増やし、終わったら自動停止できる形にする（費用最小化）。
- 候補CSV：週末バッチ未実行の週は更新されないので「前週と変わらない」は正常（ただし通知は出す）。
- Import：`vba_events.log` の詳細ログで “CSVが小さいのか/途中終了なのか” を判定してから対処する。
