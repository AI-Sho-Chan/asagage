# ASAGAKE V2 引継ぎメモ (2025-12-06)

## 1. 週末バッチの二重起動とプロセス整理

- 事象
  - VM `asagake-weekend-vm` のユーザ cron に、誤って `30 7 * * FRI` のエントリが残っており、
    - 07:30 JST に `run_weekend_only.sh` が自動起動
    - Cloud Scheduler 経由で 16:30 JST にも `run_weekend_only.sh` が起動
  - その結果、同じ `TARGET_DATE=20251205` に対して weekend バッチが **2 本並走**していた。
    - 07:30 起動分: `AM1015_j-cross refine` などが別プロセスで実行。
    - 16:30 起動分: `AM15_j-only / AM15_j-cross / AM0930_j-only` 完了後、`AM0930_j-cross coarse` を実行中。
- 対応
  - cron エントリを `30 16 * * FRI` に修正済み（07:30 のものは削除）。
  - VM 上で古い 07:30 起動分だけを kill し、16:30 起動の最新 weekend バッチのみを残した。
    - kill した PID（例）: `27855 27856 36376 57986`
    - 残した PID（例）: `45060 45061` (`run_weekend_only.sh`)、`53529` (`nightly_build_candidates.py`)、`58322` (`bt_opt30_forward AM0930_j-cross coarse`)
- メモ
  - `logs/nightly_status.txt` は「最後に状態を書いた run」に上書きされるため、複数 run が並行すると `started` / `elapsed_seconds` などが直感とズレて見える。
  - 以後、週末は **16:30 JST 起動の 1 本だけ**が動く前提で運用。

## 2. 候補集約ロジックの変更（1銘柄1プラン → 複数プラン併存）

- 従来仕様
  - `scripts/nightly_build_candidates.py` の `aggregate_candidates(...)` で、
    - 全プランの `candidates_YYYYMMDD.csv` を結合し、`output/excel/candidates_nextday.csv` / `candidates_for_YYYYMMDD.csv` を生成。
    - その際、スコア `_score` を計算したあとに
      ```python
      if "Ticker" in df.columns:
          df = df.sort_values(["Ticker", "_score"], ascending=[True, False])
          df = df.drop_duplicates(subset=["Ticker"], keep="first")
      ```
      としており、**各銘柄につきスコア最大の 1 行だけ**が残る実装だった。
  - スコアはおおよそ
    - `forward_pf_eff * (forward_winrate ** 1.2) * log1p(forward_trades) / (1 + MaxDD/1000)`
    - CorrTOPIX / VWAP 回帰により 5〜10% 程度の軽い加点。
- 課題
  - 1 銘柄が複数セッション・SignalMode で安定して強い場合でも、「最もスコアの高い 1 プラン以外」が捨てられていた。
  - 例: 8267.T, 6740.T, 7018.T, 8035.T などが複数プランで強いのに、最終候補は 1 行のみ。
- 変更内容
  - `aggregate_candidates(...)` 内の docstring とロジックを変更。
    - docstring:
      - 旧: 「pick one combo per ticker」
      - 新: 「keep all qualifying combos per ticker」（ハード条件を通過した行はすべて残す）
    - 実装:
      ```python
      # Score
      pf = num(c("forward_pf_eff"))
      win = num(c("forward_winrate"))
      trades = num(c("forward_trades"))
      dd = num("MaxDD")
      score = pf * (win ** 1.2) * (trades.add(1).apply(np.log1p)) / (1.0 + dd / 1000.0)
      # Corr / VWAP による軽い加点は従来通り

      # Sort by ticker / score but keep all combos that passed the filters
      if "Ticker" in df.columns:
          df = df.sort_values(["Ticker", "_score"], ascending=[True, False])
      else:
          df = df.sort_values(["_score"], ascending=[False])
      ```
  - ハードフィルタ（J_th, forward_win_ci_low, forward_pf_eff, forward_trades, CorrTOPIX, VWAP_revert_prob）は従来通り。
- 影響
  - 1 銘柄に対して複数セッション／SignalMode の候補が「しきい値を満たす限り」併存するようになり、粗探索段階での機会損失が減る。
  - `tools/aggregate_candidates_today.py` の fallback 集約は引き続き「1銘柄1行」だが、通常の nightly/weekend パスではこちらを通らないため影響は限定的。

## 3. 週次 WF レポート生成スクリプトの追加

- 新規ファイル: `analysis/build_weekly_wf_report.py`
  - 目的
    - 週単位で「WF ベースの候補」と「実際の約定（DEMO/LIVE）」と「期待 PnL 日次サマリ」を突き合わせて、人間が読めるテキストレポートを生成する。
  - 入力
    - `analysis/daily_trades_YYYYMMDD.csv`
      - 実際に発注されたトレードの PnL を日付別に記録。
    - `output/excel/candidates_for_YYYYMMDD.csv`
      - nightly / weekend バッチが出力する、当日用候補のスナップショット。
      - `nightly_build_candidates.py` 側で `plan_tag` 列が付いている想定（AM15_j-only など）。
    - `analysis/expected_pnl_daily.csv`
      - 既存の日次期待 PnL 集計（`date`, `expected_bp` など）。
  - 日付の扱い
    - `--week-ending YYYYMMDD` を受け取り、その日付以下の `daily_trades_*.csv` から **直近 5 営業日分**を対象にする。
    - `--week-ending` 未指定の場合は、`daily_trades_*.csv` の中で最も新しい日付を week-ending とみなす。
  - 各日のサマリ（`summarize_day(...)`）
    - Candidates 側:
      - `rows`, `unique_tickers`
      - `forward_pf_eff` / `forward_winrate` / `forward_trades` の平均値。
      - 強いコンボ数
        - 条件: `pf >= 1.3`, `winrate >= 0.6`, `trades >= 10`
        - 先頭 5 件の `Ticker@plan_tag` を例示。
    - Trades 側:
      - 約定数 `n_trades`、勝率、`pnl_bp_sum` / `pnl_bp_mean`。
    - Expected PnL:
      - `expected_pnl_daily.csv` に同じ日付があれば、`expected_bp` を併記。
    - 候補と約定の join（参考）
      - `Ticker`（候補）と `code`（daily_trades）、`session` をキーに左結合。
      - 結合後の `pnl_bp` 合計・平均を表示（WF 候補に乗っていたトレード群のざっくりした実績）。
  - 出力
    - テキストレポートを標準出力に出す。
    - 例:
      ```
      ASAGAKE weekly WF report (week ending 20251205)

      Summary by day:
      20251204:
        candidates: 78 rows, 45 tickers (pf_mean=..., win_mean=..., trades_mean=...)
          strong combos: 17 (examples: 5020.T@AM0930_j-only, ...)
        trades: 17 fills (winrate=..., pnl_bp_sum=..., pnl_bp_mean=...)
        expected_pnl: ... bp (from expected_pnl_daily.csv)
        joined (trade∩WF): ... rows, pnl_bp_sum=..., pnl_bp_mean=...
      ```

## 4. 週次 WF レポートのメール送信（state/smtp.json の再利用）

- `analysis/build_weekly_wf_report.py` にオプションを追加
  - `--email`
    - 指定時、`state/smtp.json` を読み込んで SMTP 経由でレポート本文を送信。
  - `--recipient`
    - 送信先メールアドレス（デフォルト: `shouichi.ikeda@gmail.com`）。
  - SMTP 設定
    - `state/smtp.json` から `host`, `port`, `user`, `pass` を読み込み。
    - Gmail (`smtp.gmail.com:587`) + アプリパスワードを想定（既存の history adequacy レポートと同じ設定）。
  - 実装概要
    ```python
    if args.email:
        subject = f"ASAGAKE weekly WF report (week ending {week_ending})"
        _send_email(subject, report, args.recipient)
    ```
    - `_send_email(...)` 内で `smtplib.SMTP(...).starttls().login(...).send_message(...)`。
    - 失敗時は `[warn]` ログを標準出力に出すだけで終了コードは 0（週末バッチ自体は止めない）。

    ```bash

    gsutil -m rsync -r "$HOME/asagage/output" "gs://asagage-weekend-output/output"
    ```
  - 変更後:
    ```bash
    python scripts/run_trade_analysis.py || true

    python analysis/build_weekly_wf_report.py \
      --week-ending "$TARGET_DATE" \
      --email \
      --recipient "shouichi.ikeda@gmail.com" || true
    ```

  3. `vm_run_weekend_only.sh` 相当の処理が完走すると、
     - その週の WF 候補・約定・期待 PnL を集計したテキストレポートが生成され、

  4. 別途 Cloud Scheduler `stop-weekend-vm` を安全側の時刻（例: 金曜 23:00〜土曜 0:00）に再有効化しておけば、
     - バッチ完了後のアイドリング時間を最小化しつつ、万一ハングしても VM が自動停止する。

## 7. 週末バッチ / ナイトバッチの役割整理と今後の方針

### 7-1. 金曜夜のナイトバッチについて

- `scripts/run_nightly_candidates.ps1` の挙動:
  - 平日毎晩、Windows 側で `scripts/nightly_build_candidates.py --run-type weekday` を呼び出すラッパ。
  - 金曜日だけは、本来 `scripts/run_weekend_then_nightly.ps1` を叩いて
    - 「週末バッチ（重い WF）→ナイトバッチ（軽め）→run_trade_analysis」のシーケンスを一括実行するコードが入っている。
- ただし現在は:
  - `state/disable_local_weekend.txt` が存在するため、
    - 金曜分の分岐は `nightly_build_candidates skip weekend_seq (disabled locally)` となり、
    - weekend_seq / nightly の両方をスキップして即座に exit 0 する。
  - つまり **ローカル Windows 側では既に「金曜夜のナイトバッチ」は無効化されている**。
- 方針:
  - 週末の重い WF（Top300+VWAP+60日WF）は VM 上の weekend バッチで実施し、
  - 金曜の夜に Windows で改めてナイトバッチを回す必要はない、という判断を再確認。
  - 今後も、金曜夜については
    - 「ローカルのナイトバッチは走らせない」
    - weekend は VM 専任
    を前提とする。

### 7-2. ナイトバッチ（平日）の役割

- コンセプト:
  - 週末バッチ = 「過去60営業日を使った重い総当たりテスト（定期テスト）」。
  - ナイトバッチ = 「最新の1日を足した60日ローリングで、“調子の崩れたコンビ”がないか確認する健康診断」。
- 現状の weekday ナイトバッチの主な仕事:
  - `scripts/nightly_build_candidates.py --run-type weekday`（universe-mode excel / または yahoo-top）で
    - 週末で選んだ銘柄／プランを中心に、
    - 「forward_pf」「勝率CI」がしきい値（例: PF≥1.2, CI≥0.6）を割り込んだコンビだけ再最適化する（`--reopt-degraded-only`）。
  - `scripts/run_trade_analysis.ps1` で
    - `analysis/daily_trades_YYYYMMDD.csv`
    - `analysis/expected_pnl_daily.csv`
    など「その日の約定履歴と PnL サマリ」を更新。
- 方針（ベストプラクティス案）:
  - 週末に「銘柄×時間帯×SignalMode×パラメータ」の重い探索を集中させる。
  - 平日ナイトバッチは
    1. **60日ローリングの統計更新**（新しい1日を取り込む）
    2. **しきい値割れコンビの検出と抑制**（候補から外す／ロット調整）
    3. **日次トレード結果の集計**（`daily_trades_*`, `expected_pnl_daily.csv`）
    に限定し、重い全探索は行わない。
  - 金曜夜については VM の weekend バッチに任せ、Windows 側ナイトバッチは引き続き無効（`disable_local_weekend.txt` 維持）。

### 7-3. universe-mode excel / SHINSOKU の扱い

- 背景:
  - `run_nightly_candidates.ps1` は古い名残で `--universe-mode excel` を指定しており、
    - これは元々 `SHINSOKU.xlsm` / `tick.csv` 由来の「約100銘柄」をマスターユニバースとして使うためのモードだった。
  - 現在の自動売買は `ASAGAKE.xlsm`（NewDashboard）に集約されており、SHINSOKU 系は実運用から外れている。
- 課題:
  - 逆張りスキャルの粗探索を「tick.csv の ~100銘柄」だけに限定するのは、もはや設計意図と合致しない。
  - 週末バッチ側では `yahoo-top` モード（Top300 + VWAP 回帰 + 流動性フィルタ）に移行済みで、両者が乖離している。
- 方針:
  - 中長期的には、
    - weekday ナイトバッチも `universe-mode yahoo-top` + 「週末の Top300 / Top200 常連」ベースに統一し、
    - `--excel` / `--universe-mode excel` 路線（SHINSOKU 依存）は段階的に廃止する。
  - tick.csv 由来の銘柄リストは「過去のコア銘柄」として分析用に残すにしても、  
    自動売買の主ユニバースは Top300 系に一本化する。
